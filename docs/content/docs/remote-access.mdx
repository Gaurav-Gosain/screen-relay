---
title: Remote access
description: Open the viewer or control a session from another machine with an SSH tunnel, a public HTTPS URL, or native TLS.
---

Open a session's viewer and run its client commands from another machine. A session listens on `127.0.0.1:8080` with no token, so only the VM can reach it by default. Anyone with a session's token can see and control its desktop. A session has one token and no user identity. To share less than that, create a [grant](#grants).

## Choose a path

| Path | Use it when | Token |
| --- | --- | --- |
| SSH tunnel | You have SSH access to the VM. | None |
| Behind a TLS proxy | A cloud sandbox port, nginx, Caddy, or a tunnel forwards to the VM. | Required |
| Native TLS | Clients connect straight to the VM and you have a certificate. | Required |

## SSH tunnel

1. On your machine, open the tunnel:

   ```sh
   ssh -N -L 8080:127.0.0.1:8080 user@your-vm
   ```

2. Open `http://127.0.0.1:8080` in your browser.

The session stays on loopback, so the tunnel needs no token.

## Behind a TLS proxy

1. On the VM, start the session with the public origin:

   ```sh
   screen-relay up -d --public https://desktop.example.com
   ```

   `--public` takes a bare HTTPS origin. It makes the session listen on `0.0.0.0` unless you pass `--bind`, creates a token, and accepts requests only for that host. Pages and apps on any origin can connect when they send the token.

2. Configure the proxy to:
   - forward every path with no prefix, including `/viewer.js`, `/stream`, and `/control` ([endpoints](/docs/protocol#endpoints))
   - forward WebSocket upgrades over HTTP/1.1
   - pass `Host`, `Origin`, and `Authorization` through unchanged, and keep the WebSocket subprotocol header
   - keep `Authorization` and the subprotocol header out of its logs, because the token travels in both

3. Open the viewer link that `up` printed.

Without `--tls-cert`, the engine serves plain HTTP and the proxy ends TLS. The proxy must be the only thing that can reach the port. The engine ignores `X-Forwarded-*` headers.

`up` prints a `TLS proxy` row that names the forwarding target.

## Native TLS

1. On the VM, start the session with your certificate:

   ```sh
   screen-relay up -d --tls-cert fullchain.pem --tls-key key.pem --public https://desktop.example.com
   ```

2. Open the viewer link that `up` printed.

The engine serves HTTPS itself, prints no `TLS proxy` row, and speaks HTTP/1.1 only. Client commands on the VM accept the session's own certificate even when its host name does not match, so a self-signed certificate works there.

## Tokens

screen-relay creates a 64-character lowercase hex token (256 random bits) whenever the session listens anywhere other than `127.0.0.1`, or uses `--public`.

- The token is stored in a `token` file in the session's state directory, readable only by its owner. `screen-relay status --json` shows the path as `tokenFile`.
- `screen-relay status` hides the token unless you pass `--show-token`.
- The viewer reads `#token=` from the link that `up` prints, removes it from the address bar, and uses it only on `https://` or loopback pages. Browsers never send the fragment to the server.
- Each `screen-relay up` creates a new token and ends open connections. To rotate a token, run `screen-relay down`, then `screen-relay up`.

## Grants

Grants replace the one-time `/tickets` endpoint introduced in v0.1.2. Custom viewers now send `bearer.GRANT_TOKEN` instead of `ticket.TICKET`.

A grant gives someone part of a session for a limited time without giving them the token. You create it with the token, and you can revoke it before it expires.

| Scope | What the holder can do |
| --- | --- |
| `watch` | Watch the desktop. |
| `control` | Watch the desktop and send input, in the viewer or over `/control`. |

Neither scope can read or set the clipboard, take a screenshot over HTTP, send `POST /input`, or create and revoke grants.

1. Create the grant from a machine that has the token. This example creates a watch grant that lasts 10 minutes. Without `ttl`, a grant lasts 3600 seconds, which is also the maximum.

   ```sh
   curl -s -X POST -H "Authorization: Bearer $(cat ./token)" "https://desktop.example.com/grants/watch?ttl=600"
   ```

   The response has this shape:

   ```json
   {"id":"ID","token":"GRANT_TOKEN","expires_in":600,"scope":"watch"}
   ```

   Use `/grants/control` for a control grant.

2. Build the viewer link from the grant's `token` and share it:

   | Scope | Link |
   | --- | --- |
   | `watch` | `https://desktop.example.com/#token=GRANT_TOKEN&scope=watch` |
   | `control` | `https://desktop.example.com/#token=GRANT_TOKEN&scope=control` |

   The viewer removes the fragment from the address bar, as it does for the session token. A watch link shows the desktop with no **Take control** button. A control link can take and release control, but it has no clipboard sync, and its stats panel shows no engine metrics.

3. To end the grant early, revoke it with its `id`:

   ```sh
   curl -s -X DELETE -H "Authorization: Bearer $(cat ./token)" "https://desktop.example.com/grants/ID"
   ```

When a grant is revoked or expires, the engine closes the connections opened with it and refuses new ones. Other viewers and clients stay connected. Grants are kept in memory, so `screen-relay down` ends them all.

A custom client sends the grant's `token` the same way as the session token. The [protocol](https://github.com/vercel-labs/screen-relay/blob/main/PROTOCOL.md#grants) lists the WebSocket URLs each scope opens.

## Control a session from your laptop

1. On your laptop, install the CLI. It needs Node 22 or newer and runs on any OS:

   ```sh
   npm install -g screen-relay
   ```

2. On the VM, run `screen-relay status --show-token`, and copy the token into a file named `token` on your laptop.

3. Set the target once per shell, then run client commands:

   ```sh
   export SCREEN_RELAY_URL=https://desktop.example.com
   export SCREEN_RELAY_TOKEN_FILE=./token
   screen-relay status
   screen-relay screenshot screen.png
   ```

To pass the URL and token per command, use `--url` and `--token-file` instead. Use HTTPS for any remote host. Plain HTTP works only for `localhost` or `127.0.0.1`, and redirects are not followed. The [CLI reference](/docs/cli#client-target) lists the URL rules. In Node, pass the same URL and token to `createClient` ([SDK options](/docs/sdk#options)).
